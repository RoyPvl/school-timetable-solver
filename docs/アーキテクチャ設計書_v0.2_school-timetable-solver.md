## 1. 本書の目的

本書は、`school-timetable-solver`の製造時に採用するソフトウェアアーキテクチャを固定し、次を定義する。

- モジュールの責務
- 依存方向
- クラスの配置先
- 物理ファイルの粒度
- Excel入力から時間割出力までの処理フロー
- OR-Tools CP-SATとの境界
- Hard Constraint（絶対制約）とSoft Constraint（選好制約）の実装方式
- Validation、Candidate生成、Constraint、結果検証の責務分界
- Codexが機能追加する際の変更先
- ファイルを分割する条件

本書の最重要目的は、実装者またはCodexが機能追加を行う際に、次を機械的に判断できる状態を作ることである。

```text
どのモジュールへ置くか
どのクラスへ置くか
どの公開メソッドへ実装するか
新しいクラスが必要か
既存ファイルへ同居させるか
どのテストを追加するか
```

一方で、初期製造時からクラスごとにファイルを分割しすぎることは避ける。

本書では、次の方針を採用する。

```text
論理責務:
  細かく分離する

クラス:
  ユースケースまたは業務ルール単位で分離する

物理ファイル:
  同じ責務群を中粒度でまとめる

抽象化:
  必要最小限に限定する
```

## 2. v0.1からの変更点

v0.1では、Service、Validator、Constraint等を原則として1クラス1ファイルに近い粒度で配置していた。

v0.2では、次の理由から物理ファイル構成を一段粗くする。

- 関連実装を読むためのファイル往復を減らす
- import文と定型コードを減らす
- Codexが類似クラスを見落とす可能性を下げる
- Constraintクラスを追加しただけで登録を忘れる問題を減らす
- 小規模な変更で多数のファイルが変更される状態を避ける
- 初期製造段階で不要なファイル分割判断を発生させない

変更後も、次の論理分離は維持する。

```text
1ユースケースにつき1Serviceクラス
1入力検査責務につき1Validatorクラス
1業務ルールにつき1Constraintクラス
1外部I/O種別につき1Adapterクラス
```

変更するのは、クラス設計ではなく物理ファイルの配置である。

## 3. 関連文書との関係

文書間の責務は次のとおりとする。

| 文書 | 主な責務 |
|---|---|
| 要件定義書 | 実現する機能、業務要件、受入条件 |
| 基本設計書 | Excel項目、制約内容、出力内容、運用方式 |
| 本書 | ソフトウェア内部の構造、依存方向、処理配置 |
| コーディング規約 | 命名、メソッド形式、実装記法、禁止事項 |

競合時の優先順位は次とする。

```text
1. 要件定義書
2. 本アーキテクチャ設計書
3. 基本設計書
4. コーディング規約
5. 実装上の慣習
```

コーディング規約 v0.1のうち、1クラス1ファイルを原則とする記述は、本書v0.2の中粒度ファイル構成を優先する。

ただし、次のコーディング規約は維持する。

- `Model`、`Service`、`Validator`、`Constraint`、`Adapter`等の接尾辞
- Serviceの公開メソッドは`execute()`
- Validatorの公開メソッドは`validate()`
- Constraintの公開メソッドは`apply()`
- Readerの公開メソッドは`read()`
- Writerの公開メソッドは`write()`
- `Manager`、`Processor`、`Helper`、`Utils`等の禁止
- 過剰なValidation、Interface、Factoryの禁止

## 4. アーキテクチャの結論

本システムは、次の構成を採用する。

```text
Architecture style:
  ローカル実行型モジュラーモノリス

Internal structure:
  軽量レイヤードアーキテクチャ
  + Composition Root
  + Rule-based Constraint Modules

Physical file style:
  中粒度モジュール
  同一責務群の複数クラスを同一ファイルへ配置

Execution style:
  Excelを入力とするバッチ処理

State management:
  原則ステートレス
  入力Excelと生成ファイルを正本とする

Dependency construction:
  ApplicationCompositionへ集約

Optimization:
  単一のTimetableSolverService
  strictとdiagnosticは同一モデル構築経路を使用

External boundary:
  Excel、ファイルシステム、logging、OR-Tools
```

次は採用しない。

```text
マイクロサービス
厳密なClean Architecture
Domain-Driven Designの戦術パターン一式
Repository Pattern
イベント駆動
プラグインアーキテクチャ
1クラス1ファイルの機械的適用
Base / Factory / Managerによる抽象化層
```

本システムの複雑性は、外部システム連携ではなく、入力データの整合性と制約最適化にある。

したがって、レイヤー数やファイル数を増やすより、業務ルールの配置先と依存方向を明確にすることを優先する。

## 5. 設計原則

### 5.1 論理分離と物理分割を区別する

次を維持する。

```text
RuleResolverServiceとCandidateBuilderServiceは別クラス
ValidateResultServiceとDiagnosticServiceは別クラス
各Hard Constraintは別クラス
各Soft Constraintは別クラス
各Validatorは別クラス
```

ただし、同じ責務群のクラスは同じファイルへ配置する。

```text
RuleResolverService
CandidateBuilderService
  → planning_services.py

ValidateResultService
DiagnosticService
  → result_services.py

全Hard Constraint
  → hard_constraints.py

全入力Validator
  → input_validators.py
```

### 5.2 抽象化ではなく同居でファイル数を減らす

ファイル数を減らすために、次のような統合クラスは作らない。

```text
ConstraintManager
ValidationManager
ServiceCoordinator
RuleProcessor
BaseConstraint
ConstraintFactory
```

複数クラスを同じモジュールに置くが、クラス責務は統合しない。

### 5.3 変更先を一意にする

新しい仕様の実装先は次の順で決定する。

```text
外部形式の変更か
  → adapter

入力値そのものの不正か
  → validator

単一候補だけで配置不能と判断できるか
  → CandidateBuilderService

複数配置の選択状態を必要とする絶対条件か
  → Hard Constraint

複数配置の選択状態を必要とする選好条件か
  → Soft Constraint

生成結果の正当性確認か
  → ValidateResultService

利用者向けの原因説明か
  → DiagnosticService
```

### 5.4 同じルールを複数箇所へ重複実装しない

CandidateBuilderで除外した条件を、同じ意味のConstraintとして追加しない。

ただし、生成結果の独立検証ではHard Constraint相当の検査を別ロジックで実施する。

これは重複実装ではなく、ソルバー実装自体の不具合を検出する独立検証である。

### 5.5 外部入力は境界で一度だけ検証する

Excel形式検査はAdapter、意味整合性検査はValidatorで一度だけ行う。

検証済みの`InputDataModel`をService間で再検証しない。

### 5.6 年度固有条件をコードへ埋め込まない

次をPythonコードへ直接記述しない。

```text
年度
月
特定日付
校舎表示名
クラス表示名
教師表示名
受験学年名
お盆休みの日付
最大コマ数
許可時限
ペナルティ重み
```

これらはExcel入力または設定Modelから取得する。

## 6. アーキテクチャ品質目標

優先順位は次のとおりとする。

```text
1. 正確性
2. ルール追跡可能性
3. 再現性
4. 変更箇所の局所化
5. 可読性
6. テスト容易性
7. 診断可能性
8. 実行性能
9. 拡張性
```

### 6.1 正確性

- Hard Constraint違反を含む時間割を正常結果として出力しない。
- ソルバー結果をOR-Toolsから独立した処理で再検証する。
- 入力不備、候補不足、`INFEASIBLE`、内部不具合を区別する。

### 6.2 ルール追跡可能性

各業務ルールは`rule_id`により追跡する。

```text
要件定義
  ↓
rule_id
  ↓
Constraint Class / Candidate判定
  ↓
Validation Issue / Diagnostic
  ↓
Test Name / Log
```

### 6.3 再現性

同一の入力ファイル、アプリケーションバージョン、乱数シード、OR-Tools設定から、原則として同一結果を再現できることを優先する。

全クラス実データを現実的な時間で解く通常設定では並列探索を使用する。結果の再現性を最優先する実行では、CLIから1ワーカーを選択する。

```text
通常:
  num_search_workers = 8

再現性優先:
  num_search_workers = 1

random_seed = CLIまたは既定設定から取得
```

ワーカー数は解集合またはHard Constraintを変更せず、探索順だけを変更する。並列探索の結果も、実教室割当後に独立結果検証を通過した場合だけ正式出力とする。

### 6.4 変更箇所の局所化

| 変更種別 | 主変更ファイル | 主クラス |
|---|---|---|
| Excel入力シート・列変更 | `adapter/excel_input_adapter.py` | `ExcelInputReaderAdapter` |
| Excel出力レイアウト変更 | `adapter/excel_output_adapter.py` | 各Writer Adapter |
| 入力整合性チェック追加 | `validator/input_validators.py` | `XxxValidator` |
| ルール解決方式変更 | `service/planning_services.py` | `RuleResolverService` |
| Candidate生成方式変更 | `service/planning_services.py` | `CandidateBuilderService` |
| Hard Constraint追加 | `constraint/hard_constraints.py` | `XxxConstraint` |
| Soft Constraint追加 | `constraint/soft_constraints.py` | `XxxConstraint` |
| ソルバー設定変更 | `service/solver_service.py` | `TimetableSolverService` |
| 結果検証追加 | `service/result_services.py` | `ValidateResultService` |
| 診断文変更 | `service/result_services.py` | `DiagnosticService` |
| 全体実行順序変更 | `service/generation_services.py` | `GenerateTimetableService` |
| 依存構成変更 | `composition.py` | `ApplicationComposition` |

```text
main
  ↓
composition
  ↓
service
  ├── validator
  ├── constraint
  ├── model
  └── I/O Protocol

  ├── Excel Input
```

| `model` | レイヤー間で受け渡す内部データ |
| `adapter` | Excel、ファイル、ログ等の外部形式との変換 |


循環importは禁止する。

循環が発生した場合は、Model配置または責務分界が誤っているものとして設計を見直す。

## 11. ファイル分割方針

### 11.1 原則

```text
1クラス1責務:
  必須

1クラス1ファイル:
  原則としない

同一責務群を同一ファイルへ配置:
  必須
```

### 11.2 同一ファイルへ配置する基準

次の条件を満たすクラスは同じファイルへ配置する。

- 同じレイヤーに属する
- 同じ処理フェーズで使用される
- 同じ外部依存を使用する
- 変更理由が近い
- 合計規模が読解可能な範囲に収まる

### 11.3 ファイルを分割する検討条件

次のいずれかが発生した場合にのみ、ファイル分割を検討する。

- 1ファイルが概ね500行を超えた
- 主要な公開クラスが6個を超えた
- 外部依存が明確に異なるクラス群が生じた
- 一方の変更で無関係なテストが頻繁に影響を受ける
- 複数人が継続的に同一ファイルを変更し、競合が常態化した
- Codexが対象クラスを誤認する事例が実際に繰り返された
- モジュール名では責務群を表現できなくなった

これらは自動分割条件ではなく、設計レビューを開始する条件とする。

### 11.4 分割時の単位

分割する場合も、1クラス1ファイルへ戻さない。

業務上の責務群で分割する。

例：`hard_constraints.py`が肥大化した場合

```text
constraint/
├── solver_context.py
├── hard_requirement_constraints.py
├── hard_resource_constraints.py
├── hard_schedule_constraints.py
└── soft_constraints.py
```

| ファイル | 収容するConstraint |
|---|---|
| `hard_requirement_constraints.py` | 必要コマ数、固定授業 |
| `hard_resource_constraints.py` | 教師・クラス・教室重複、校舎移動 |
| `hard_schedule_constraints.py` | 日別上限、連続コマ、連続登校 |

### 11.5 禁止する分割理由

次の理由だけではファイルを分割しない。

- クラスを新しく作った
- ファイルが200行を超えた
- 将来増える可能性がある
- 1クラス1ファイルが一般的に見える
- Codexが編集しやすそうという推測だけがある
- 名前が長くなった

## 12. Model設計

Modelは、外部形式およびOR-Toolsから独立した内部データである。

原則として次を使用する。

```python
@dataclass(frozen=True, slots=True)
class XxxModel:
    ...
```

Modelへ重い業務ロジック、外部I/O、OR-Tools式を持たせない。

### 12.1 `master_models.py`

| Model | 主な責務 |
|---|---|
| `CampusModel` | 校舎ID、表示名、移動グループ |
| `RoomModel` | 教室ID、所属校舎、有効状態 |
| `TeacherModel` | 教師ID、表示名、担当可能教科、基準校舎 |
| `ClassModel` | クラスID、学部、学年、受験区分、所属校舎 |
| `SubjectModel` | 教科ID、表示名 |
| `PeriodModel` | 時限ID、順序、開始・終了時刻 |

### 12.2 `input_models.py`

Excelから読み込む設定および業務入力を配置する。

| Model | 主な責務 |
|---|---|
| `GenerationSettingsModel` | 生成モード、探索時間、乱数シード、出力設定 |
| `CalendarDayModel` | 日付、開館可否、利用可能時限 |
| `LessonRequirementModel` | クラス、教科、必要コマ数、担当候補 |
| `TeacherAvailabilityModel` | 教師、日付、時限ごとの勤務可否・希望 |
| `RoomAvailabilityModel` | 教室、日付、時限ごとの利用可否 |
| `FixedLessonModel` | 固定授業の日時、教師、教室 |
| `PlacementRuleModel` | Excel上の汎用配置ルール |
| `PenaltyWeightModel` | Soft Constraintの有効状態と重み |
| `InputDataModel` | 全入力Modelを束ねる |

### 12.3 `solver_models.py`

OR-Tools型を含めてはならない。

| Model | 主な責務 |
|---|---|
| `EffectiveClassDateRuleModel` | クラス・日付単位の解決済み条件 |

| `CandidateRejectionSummaryModel` | 候補除外数のrule_id別集計 |
| `CandidateBuildResultModel` | Candidate一覧と除外サマリ |
| `PenaltyResultModel` | 選好違反の種類、件数、加重点 |
| `SolverStatisticsModel` | ステータス、時間、変数数、目的値 |
| `SolverResultModel` | OR-Tools結果を内部形式へ変換した結果 |

`CandidateSlotModel`は授業要求・日付・時限・固定教師・校舎を持ち、教室IDを持たない。現入力契約では同一校舎内の教室に個別条件がないため、教室次元は探索後に決定する。

### 12.4 `result_models.py`

## 15. Validator設計

全入力Validatorは`validator/input_validators.py`へ配置する。

初期Validatorは次とする。

| Class | 責務 |
|---|---|
| `ReferenceIntegrityValidator` | ID重複、参照先不存在、担当関係の整合性 |
| `FixedLessonValidator` | 固定授業同士および勤務不可との矛盾 |
| `RuleConflictValidator` | 同一優先順位のルール競合 |
| `CapacityFeasibilityValidator` | 必要コマに対する明白な供給枠不足 |

各Validatorは次の形式とする。

```python
class XxxValidator:
    def validate(self, input_data: InputDataModel) -> list[ValidationIssueModel]:
        ...
```

### 15.1 Adapterが担当する形式検査

- ファイルを開けるか
- 必須シートが存在するか
- 必須ヘッダーが存在するか
- セル値を期待型へ変換できるか
- 日付、時刻、真偽値の形式が正しいか
- 入力スキーマバージョンが対応範囲か

### 15.2 Validatorが担当する意味検査

- IDの重複
- 参照先IDの不存在
- 固定授業の内部矛盾
- 同一優先順位のルール競合
- 必要コマ数に対して明白に供給枠が不足する状態

### 15.3 再Validation禁止

`InputDataModel`がServiceへ渡った後は次を再検証しない。

```text
ID存在確認
必須項目確認
日付形式
数値型
重複ID
```

内部不変条件が破られた場合は、黙示的なフォールバックを行わず内部不具合として失敗させる。

## 16. Rule Resolution設計

### 16.1 ルールの正本

年度、季節、受験区分、校舎、期間、許可時限、上限等の正本はExcelの配置ルールとする。

Pythonコードは次を直接判定しない。

```text
current_date.month >= 8
class_name == "梅光園3A"
weekday == Sundayなら休館
8月7日から16日ならお盆休み
```

### 16.2 優先順位

ルール競合は`priority`列により解決する。

```text
priorityが高いルールを優先する
```

暗黙の「条件が具体的な方を優先する」は採用しない。

同一対象、同一日付、同一設定項目に、同一priorityで異なる値が存在する場合は入力エラーとする。

### 16.3 解決結果

RuleResolverServiceは事前に次の索引を生成する。

```text
class_id + date
  → EffectiveClassDateRuleModel

teacher_id + date
  → EffectiveTeacherDateRuleModel
```

CandidateBuilderおよびConstraintは、解決済み値だけを参照する。

## 17. Candidate設計

Candidateはソルバー変数を作成する最小単位である。

```text
CandidateSlotModel
  requirement_id
  class_id
  subject_id
  teacher_id
  campus_id
  date
  period_id
```

現入力契約では、同一校舎内の有効教室は交換可能である。Candidateへ教室IDを含めると、同じ日時解に対して教室の並べ替えだけが異なる大量の対称解を作るため、探索変数から教室次元を除外する。

### 17.1 CandidateBuilderで除外してよい条件

単一Candidateだけを見て、他Candidateの選択状態に関係なく不可能と判断できる条件に限定する。

- 休館日
- 当該日に存在しない時限
- クラスに許可されていない時限
- 教師が勤務不可の日時
- 無効化された校舎、教師、クラス

### 17.2 CandidateBuilderで判定してはいけない条件

- 教師重複
- クラス重複
- 教室重複
- 必要コマ数
- 1日最大コマ数
- 教師の最大連続コマ数
- クラスの連続登校日数
- 校舎移動に必要な空き時限
- 公休日数
- 空きコマ数

### 17.3 二重実装禁止

CandidateBuilderで除外済みの単一候補条件を、同じ意味のHard Constraintとして再実装しない。

```text
許可時限
  → CandidateBuilderService
  → AllowedPeriodConstraintは作らない
```

結果検証では許可時限を再検査する。

### 17.4 Candidate除外サマリ

全除外Candidateを保持せず、初期実装では次を集計する。

```text
requirement_id
rule_id
rejected_count
remaining_count
```

## 19. OR-Tools変数設計

### 19.1 基本配置変数

CandidateごとにBoolVarを1つ作る。

```text
x[candidate_id] ∈ {0, 1}
```

`x = 1`は、該当授業を該当日時、固定教師、所属校舎へ配置することを意味する。教室IDは探索成功後に`AssignRoomsService`が決定する。

全組合せに変数を作らず、CandidateBuilderが生成した候補だけを変数化する。

### 19.2 未配置変数

Diagnostic Modeでは、授業要求ごとに未配置数を表すIntVarを作る。

```text
unplaced[requirement_id] >= 0
```

Strict Modeでは未配置を許可しない。

### 19.3 補助変数

次の場合だけ作る。

- クラスが特定日に登校するか
- 教師が特定日に勤務するか
- 連続コマ数を表現する必要がある
- Soft Constraint違反数を数える
- 校舎移動の有無を表す

将来使う可能性だけで補助変数を作らない。

### 19.4 変数名

業務キーを含める。

```text
x__R001__2026-07-20__P1__T001
unplaced__R001
class_day__C001__2026-07-20
```

表示名ではなくIDを使用する。

## 20. Constraint設計

全Hard Constraintは`constraint/hard_constraints.py`へ配置する。

全Soft Constraintは`constraint/soft_constraints.py`へ配置する。

### 20.1 Hard Constraint

| Class | rule_id | 責務 |
|---|---|---|
| `RequiredLessonCountConstraint` | `H06` | 必要コマ数を満たす |
| `TeacherOverlapConstraint` | `H01` | 同時刻の教師重複禁止 |
| `ClassOverlapConstraint` | `H02` | 同時刻のクラス重複禁止 |
| `CampusRoomCapacityConstraint` | `H03` | 同一校舎・同時刻の授業数を有効教室数以下にする |
| `ClassDailyLimitConstraint` | `H07` | クラス・授業要求の日別上限 |
| `TeacherDailyLimitConstraint` | `H08` | 教師の日別上限 |
| `TeacherConsecutivePeriodConstraint` | `H09` | 教師の連続コマ上限 |
| `ConsecutiveAttendanceConstraint` | `H10` | クラスの連続登校上限 |
| `TeacherSingleCampusPerDayConstraint` | `H11` | 同一教師の同日複数校舎を禁止する |

`TeacherOverlapConstraint`と`ClassOverlapConstraint`は、必要総コマ数が候補日時枠数と一致する対象について、各日時枠の選択数を`1`へ強化してよい。これは`H06`と各重複禁止から論理的に必ず導かれる冗長制約であり、正しい解を削らず伝播だけを強める。

各Constraintは次の形式とする。

```python
class XxxConstraint:
    rule_id = "H_..."

    def apply(self, context: SolverContext) -> None:
        ...
```

### 20.2 Soft Constraint

| Class | rule_id | 責務 |
|---|---|---|
| `LateToEarlyConstraint` | `S_LATE_TO_EARLY` | 6限翌日の1限を抑制 |
| `TeacherGapConstraint` | `S_TEACHER_GAP` | 教師の空きコマを抑制 |
| `PreferredDayOffConstraint` | `S_PREFERRED_DAY_OFF` | 公休日数不足を抑制 |
| `ClassScheduleBalanceConstraint` | `S_CLASS_SCHEDULE_BALANCE` | クラスの授業日偏りを抑制 |
| `CampusTransferPenaltyConstraint` | `S_CAMPUS_TRANSFER` | 許可された移動回数を抑制 |

### 20.3 Constraint登録

`hard_constraints.py`および`soft_constraints.py`の末尾に、標準登録tupleを定義する。

```python
DEFAULT_HARD_CONSTRAINTS = (
    RequiredLessonCountConstraint(),
    TeacherOverlapConstraint(),
    ClassOverlapConstraint(),
    CampusRoomCapacityConstraint(),
    ClassDailyLimitConstraint(),
    TeacherDailyLimitConstraint(),
    TeacherConsecutivePeriodConstraint(),
    ConsecutiveAttendanceConstraint(),
    TeacherSingleCampusPerDayConstraint(),
)
```

```python
DEFAULT_SOFT_CONSTRAINTS = (
    LateToEarlyConstraint(),
    TeacherGapConstraint(),
    PreferredDayOffConstraint(),
    ClassScheduleBalanceConstraint(),
    CampusTransferPenaltyConstraint(),
)
```

Constraintクラスを追加した場合は、同じファイル内で登録tupleも更新する。

Registry専用ファイルまたはConstraintFactoryは作らない。

### 20.4 適用順序

登録tupleの順序を適用順序とする。

順序はConstraint間の直接依存を意味しない。

ログと調査時の一貫性のために固定する。

### 20.5 Soft Constraintの目的関数

各Soft Constraintは、`SolverContext`へ次を登録する。

```text
rule_id
penalty_variable
weight
human-readable key
```

`TimetableSolverService`が全ペナルティ項を集計し、`CpModel.Minimize()`を1回だけ呼ぶ。

Soft Constraint自身は目的関数を設定しない。

## 21. Strict ModeとDiagnostic Mode

Strict ModeとDiagnostic Modeで別のSolverクラスを作らない。

単一の`TimetableSolverService`がモードを受け取り、必要コマ数制約と目的関数のみを切り替える。

### 21.1 Validate-only Mode

```text
Input読込
  ↓
Input Validation
  ↓
Validation Report出力
```

OR-Toolsを起動しない。

### 21.2 Strict Mode

```text
assigned_count == required_count
unplaced variableなし
Hard Constraint違反不可
Soft Constraint総ペナルティ最小化
```

### 21.3 Diagnostic Mode

```text
assigned_count + unplaced_count == required_count
安全に関わるHard Constraintは維持
未配置を高ペナルティで許容
未配置数を最優先で最小化
残りのSoft Constraintを次順位で最小化
```

### 21.4 目的関数

Diagnostic Modeでは、未配置1コマの重みをSoft Constraint全違反の理論上限より大きくする。

ただし、係数を無制限に大きくしない。

入力上限からSoft Penaltyの最大値を計算し、安全な係数範囲を検査する。

## 25. エラー分類

エラーは次のカテゴリで区別する。

| Category | 例 | 終了コード方針 |
|---|---|---:|
| Input Format Error | 必須シートなし、型変換失敗 | 2 |
| Input Semantic Error | 参照先不存在、ルール競合 | 3 |
| Candidate Insufficiency | 候補ゼロ、明白な供給不足 | 4 |
| Solver Infeasible | Strict Modeで解なし | 5 |
| Result Validation Error | Solver結果がHard Constraint違反 | 6 |
| Internal Error | 想定外例外、内部不変条件違反 | 10 |

独自例外クラスを初期段階から大量に作らない。

必要最小限の例外カテゴリのみ定義し、詳細は`ValidationIssueModel`またはログへ保持する。

## 32. 最終決定

本プロジェクトのアーキテクチャとして、次を採用する。

```text
Architecture:
  ローカル実行型モジュラーモノリス

Layer:
  model
  service
  validator
  constraint
  adapter
  composition

Physical files:
  同一責務群を中粒度ファイルへ集約
  初期実装は約15〜18 Pythonファイル

Class boundary:
  1ユースケースまたは1業務ルールにつき1クラス

File boundary:
  1クラス1ファイルにはしない

Composition:
  ApplicationCompositionに依存生成を集約

Validation:
  Excel形式はAdapter
  入力意味はValidator
  内部Modelは再検証しない

Candidate:
  単一候補だけで判断できる不可能枠のみ除外

Constraint:
  複数配置を必要とするHard／Soft条件を実装
  1業務ルール1クラス
  Hard／Softごとに1ファイルへ集約

Solver:
  TimetableSolverServiceを単一実装
  Strict／Diagnosticで共有

Result validation:
  Constraintを再利用せず独立検証

Codex control:
  AGENTS.mdの配置表
  固定されたクラス接尾辞と公開メソッド
  Constraint登録tuple
  Architecture Test

Future split:
  ファイル肥大化または実害発生後に
  業務責務群単位で分割する
```

本設計では、ファイル数を減らすために責務を曖昧化しない。

また、Codexの判断を減らすためにファイルを過剰分割しない。

```text
設計は細かくする。
配置は粗くする。
抽象化は増やさない。
逸脱はテストで防ぐ。
```
