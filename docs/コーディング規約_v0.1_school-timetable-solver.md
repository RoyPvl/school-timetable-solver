| 項目 | 内容 |

| システム名称 | 時間割解決システム |
| Gitプロジェクト名 | `school-timetable-solver` |

## 1. 本書の目的

本書は、`school-timetable-solver` の製造・改修時に、実装者およびCodexが次の問題を起こさないための規約である。

- 意味の不明な関数を既存ファイルへ増設する
- 同じ責務を複数のクラスへ重複実装する
- `helper`、`util`、`manager` 等へ処理を逃がす
- OR-Tools固有処理をサービスやExcel入出力へ拡散する
- 各レイヤーで同じ入力値を繰り返し検証する
- 年度、校舎名、クラス名、月等をコードへ直接埋め込む
- 制約追加のたびに既存制約を壊す
- 将来用途を理由に不要な抽象化やインターフェースを追加する

本書で最も重視する原則は次のとおりである。

```text
1. クラスの責務をユースケースまたは業務ルール単位で固定する
2. クラス種別ごとに公開メソッド名を固定する
3. 新しい処理を追加する場所を機械的に決定できるようにする
4. 外部入力の検証は境界で一度だけ行う
5. 内部データは検証済みとして扱い、再検証しない
6. OR-Toolsへの制約追加はconstraint配下だけで行う
7. Excel固有仕様はadapter配下だけで扱う
8. 仕様にない抽象化、分岐、フォールバックを追加しない
```

---

## 2. 優先順位

実装時は、次の順序で品質を評価する。

```text
1. 仕様どおりに動く
2. どの業務ルールをどこで実装したか追跡できる
3. 読める
4. テストできる
5. 改修時に変更箇所を限定できる
6. 必要になった時点で分割・抽象化できる
```

初期段階では、汎用フレームワーク化、過剰な拡張性、短いコード、抽象化の美しさを優先しない。

## 3. 技術・記法の基本方針

### 3.1 Pythonの基本記法

- PythonコードはPEP 8を基礎とする。
- 型ヒントを必須とする。
- 公開クラス、公開メソッド、複雑な業務ロジックにはdocstringを付ける。
- `from __future__ import annotations` はプロジェクト内で統一して使用する。
- パスは`pathlib.Path`で扱う。
- 日付は`datetime.date`、日時は`datetime.datetime`で扱う。
- 金額計算は存在しないため、`Decimal`を機械的に導入しない。
- ログ出力に`print()`を使用しない。コマンドラインの最終表示を除き、標準`logging`を使用する。

### 3.2 コード品質ツール

設定値は`pyproject.toml`を正本とし、ローカル実行と継続的インテグレーションで同じコマンドを使用する。

```text
ruff:
  lintおよびformat

mypy:
  型検査

pytest:
  テスト
```

ツール設定を複数ファイルへ分散させない。

## 4. 配置先の基本構造

本規約では詳細なアーキテクチャ設計を定義しないが、処理の配置先を固定するため、次の責務境界を前提とする。

```text
src/
└── school_timetable_solver/
    ├── main.py
    ├── model/
    ├── service/
    ├── validator/
    ├── constraint/
    │   ├── hard/
    │   └── soft/
    ├── adapter/
    └── composition/

tests/
├── unit/
├── integration/
└── fixtures/
```

各ディレクトリの責務は次のとおりである。

| 配置先 | 責務 |
|---|---|
| `model` | 検証済み内部データ、列挙型、処理結果を表す |
| `service` | 利用者または上位処理から見たユースケースを実行する |
| `validator` | 外部入力境界または生成結果境界で検証する |
| `constraint/hard` | OR-Toolsへ絶対制約を追加する |
| `constraint/soft` | OR-Toolsへペナルティ項を追加する |
| `adapter` | Excel、ファイル、ログ等の外部入出力を扱う |
| `composition` | Adapter、Validator、Constraint、Serviceを生成して注入する |
| `main.py` | 引数を受け、CompositionからServiceを取得し、1回呼び出す |

## 5. クラス種別と命名規則

### 5.1 接尾辞を必須とするクラス

| 種別 | 接尾辞 | 例 |
|---|---|---|
| 内部データ | `Model` | `TeacherModel`、`TimetableResultModel` |
| ユースケース・処理本体 | `Service` | `GenerateTimetableService` |
| 外部入出力 | `Adapter` | `ExcelInputReaderAdapter` |
| 入力・結果検証 | `Validator` | `ReferenceIntegrityValidator` |
| 絶対制約・選好制約 | `Constraint` | `TeacherOverlapConstraint` |
| 変換専用 | `Mapper` | `WorksheetRowMapper` |
| 作業中コンテキスト | `Context` | `SolverContext` |
| 依存組み立て | `Composition` | `ApplicationComposition` |
| 複雑な生成処理 | `Factory` | 原則禁止。必要性を説明できる場合のみ |

### 5.2 禁止する曖昧な名前

次の単語をクラス名またはモジュール名の主要語として使用しない。

```text
Manager
Processor
Handler
Helper
Helpers
Util
Utils
Utility
Common
Base
Misc
Core
Engine
Coordinator
Support
```

`Solver`はOR-Toolsによる探索実行を表す場合のみ使用できる。

### 5.3 モデル命名

内部データを表すクラスには`Model`を付ける。

推奨例：

```text
CampusModel
RoomModel
TeacherModel
ClassModel
LessonRequirementModel
TeacherLeaveModel
FixedLessonModel
PlacementRuleModel
PenaltyWeightModel
InputDataModel
CandidateSlotModel
ScheduledLessonModel

ValidationReportModel

```

避ける例：

```text

Data
Result

```

### 5.4 列挙型命名

列挙型には`Enum`接尾辞を付けない。値は大文字スネークケースとする。

```python
class GenerationMode(str, Enum):
    VALIDATE_ONLY = "validate_only"
    DIAGNOSTIC = "diagnostic"
    STRICT = "strict"
```

## 6. ファイル命名とクラス配置

### 6.1 ファイル名

- ファイル名は`snake_case.py`とする。
- 原則として、1ファイルに主要な公開クラスを1つ置く。
- ファイル名は主要クラス名をスネークケースへ変換した名称と一致させる。

```text
GenerateTimetableService
  → generate_timetable_service.py

TeacherOverlapConstraint
  → teacher_overlap_constraint.py

ExcelInputReaderAdapter
  → excel_input_reader_adapter.py
```

### 6.2 複数クラスを同じファイルへ置いてよい場合

次のいずれかに限定する。

- 1つの主クラスだけで使用する非公開クラス
- 密接に関連する小規模な`Model`群
- 同じ意味領域の列挙型群
- テスト内のFakeクラス

モデルは次のように意味領域ごとにまとめてもよい。

```text
model/master_models.py
model/input_models.py
model/rule_models.py
model/solver_models.py
model/result_models.py
```

### 6.3 再エクスポート禁止

`__init__.py`で大量のクラスを再エクスポートしない。利用側は定義元モジュールから直接importする。

悪い例：

```python
from school_timetable_solver.model import TeacherModel
```

推奨例：

```python
from school_timetable_solver.model.master_models import TeacherModel
```

## 7. 公開メソッド名の固定

クラス種別ごとに公開メソッド名を固定する。Codexは、理由なく別名の公開メソッドを追加してはならない。

| クラス種別 | 原則となる公開メソッド | 戻り値 |
|---|---|---|
| `XxxService` | `execute(...)` | ユースケース結果Model |
| `XxxValidator` | `validate(...)` | `list[ValidationIssueModel]` |
| `XxxConstraint`（Hard） | `apply(context)` | `None` |
| `XxxConstraint`（Soft） | `apply(context)` | `PenaltyTermModel`または`None` |
| `XxxInputReaderAdapter` | `read(path)` | `InputDataModel`等 |
| `XxxOutputWriterAdapter` | `write(model, path)` | `None` |
| `XxxMapper` | `map(source)` | 変換後Model |
| `XxxRepositoryAdapter` | `load(...)`、`save(...)` | 対象Modelまたは`None` |
| `XxxComposition` | `create_<use_case>_service()` | Service |

### 7.1 Serviceは公開メソッドを1つにする

1つのServiceは1つのユースケースを表し、公開メソッドは原則`execute()`の1つだけとする。

```python
class GenerateTimetableService:
    def execute(
        self,
        request: GenerationRequestModel,
    ) -> GenerationResultModel:
        ...
```

次のような公開メソッドの増設は禁止する。

```python
service.load()
service.prepare()
service.run_solver()
service.export()
service.process()
```

これらが必要なら、非公開メソッドにするか、別の責務を持つクラスへ移す。

### 7.2 Constraintの公開メソッドを`apply()`に統一する

```python
class TeacherOverlapConstraint:
    rule_id = "H02_TEACHER_OVERLAP"

    def apply(self, context: SolverContext) -> None:
        ...
```

次の別名を作らない。

```text
add
build
register
set
create_constraints
apply_teacher_rule
```

### 7.3 Validatorの公開メソッドを`validate()`に統一する

```python
class ReferenceIntegrityValidator:
    def validate(
        self,
        input_data: InputDataModel,
    ) -> list[ValidationIssueModel]:
        ...
```

Validatorは例外を投げて処理を制御するのではなく、原則として検証結果を返す。

## 8. 新しい処理の配置決定ルール

新しい関数またはクラスを作る前に、次の順序で配置先を決定する。

```text
Q1. Excel、ファイル、OS、外部ライブラリの形式を直接扱うか
  Yes → adapter

Q2. 外部形式と内部Modelを相互変換するだけか
  Yes → adapter内のMapper、またはXxxMapper

Q3. 外部入力の形式、参照整合性、最低限の実行可能性を検査するか
  Yes → validator

Q4. OR-ToolsのCpModelへ絶対条件を追加するか
  Yes → constraint/hard

Q5. OR-Toolsの目的関数へペナルティを追加するか
  Yes → constraint/soft

Q6. 複数の処理を順序立てて実行し、利用者向け結果を返すか
  Yes → service

Q7. 値や処理結果を保持するだけか
  Yes → model

Q8. 依存オブジェクトを生成・注入するか
  Yes → composition

Q9. 上記のどれにも該当しないか
  Yes → 新規追加しない。責務の定義から見直す
```

この判定を行わず、既存ファイルの末尾へ関数を追加してはならない。

## 9. Serviceの設計規約

### 9.1 Serviceはユースケース単位で切る

初期の主要Serviceは次を標準とする。

| Service | ユースケース |
|---|---|
| `ValidateInputService` | 入力Excelを読み、検証結果を返す |
| `GenerateTimetableService` | 厳密生成または診断生成を実行する |
| `ValidateResultService` | 生成結果を独立検証する |
| `CandidateBuilderService` | 授業要求ごとの配置候補を作る |
| `TimetableSolverService` | OR-Toolsモデルを構築し探索する |
| `DiagnosticService` | 未配置・制約衝突を人間向け結果へ整理する |

`CandidateBuilderService`と`TimetableSolverService`は利用者向けユースケースではないが、計算処理の大きな責務境界としてServiceに置く。

### 9.2 Serviceに置いてよい処理

- 処理順序の制御
- Model同士を使った業務判断
- Candidate、Constraint、Solverの呼び出し
- AdapterまたはValidatorのインターフェース呼び出し
- 処理結果Modelの生成
- エラーを上位へ伝えるための文脈付与

### 9.3 Serviceに置いてはいけない処理

- Excelセル番地の直接参照
- ワークシート名の判定
- OR-Tools変数を直接列挙して制約を追加する処理
- `openpyxl`オブジェクト操作
- 特定校舎名やクラス名による分岐
- 同じ入力値の再検証
- ファイルパスの自動推測
- ログを出して失敗を握りつぶす処理

### 9.4 Constructor Injectionを使用する

依存関係はコンストラクタで明示的に受け取る。

```python
class GenerateTimetableService:
    def __init__(
        self,
        input_reader: ExcelInputReaderAdapter,
        input_validators: Sequence[InputValidator],
        candidate_builder: CandidateBuilderService,
        solver_service: TimetableSolverService,
        result_validator: ValidateResultService,
        output_writer: ExcelOutputWriterAdapter,
    ) -> None:
        self._input_reader = input_reader
        self._input_validators = tuple(input_validators)
        self._candidate_builder = candidate_builder
        self._solver_service = solver_service
        self._result_validator = result_validator
        self._output_writer = output_writer
```

Service内部でAdapterやValidatorを生成しない。

## 10. Constraintの設計規約

### 10.1 業務ルール1件につきConstraintクラス1つ

Hard Constraint（絶対制約）およびSoft Constraint（選好制約）は、業務ルール単位でクラスを分ける。

推奨例：

```text
constraint/hard/required_lesson_count_constraint.py
  RequiredLessonCountConstraint

constraint/hard/teacher_overlap_constraint.py
  TeacherOverlapConstraint

constraint/hard/class_overlap_constraint.py
  ClassOverlapConstraint

constraint/hard/room_overlap_constraint.py
  RoomOverlapConstraint

constraint/hard/allowed_period_constraint.py
  AllowedPeriodConstraint

constraint/hard/daily_period_limit_constraint.py
  DailyPeriodLimitConstraint

constraint/hard/consecutive_attendance_constraint.py
  ConsecutiveAttendanceConstraint

constraint/hard/teacher_consecutive_period_constraint.py
  TeacherFirstLastPeriodConstraint

constraint/soft/late_to_early_constraint.py
  LateToEarlyConstraint

constraint/soft/preferred_day_off_constraint.py
  PreferredDayOffConstraint

constraint/soft/class_schedule_balance_constraint.py
  ClassScheduleBalanceConstraint
```

### 10.2 ConstraintはOR-Tools式の構築だけを行う

Constraintに置いてよい処理：

- `CpModel.Add()`の呼び出し
- BoolVar、IntVar、LinearExprを使った制約式の構築
- 対象となる既存変数の検索
- ルールに対応するペナルティ変数の生成
- `rule_id`、ペナルティ名等の付与

Constraintに置いてはいけない処理：

- Excel値の読み込み
- 入力値の妥当性検査
- Candidateの新規生成
- 教師・クラスのマスタ補完
- 日付やクラス名に対するハードコード分岐
- 結果Excelへの書き込み
- 例外を握りつぶす処理

### 10.3 ルールIDを必須とする

各Constraintは、要件定義・制約定義と追跡可能な`rule_id`を持つ。

```python
class TeacherOverlapConstraint:
    rule_id = "H02_TEACHER_OVERLAP"

    def apply(self, context: SolverContext) -> None:
        ...
```

ルールIDはログ、診断結果、テスト名でも使用する。

### 10.4 Constraint間で直接呼び出さない

Constraint AからConstraint Bを呼び出してはならない。適用順序は`TimetableSolverService`または`Composition`から注入されたリストで制御する。

```python
for constraint in self._hard_constraints:
    constraint.apply(context)
```

### 10.5 OR-Toolsのimport範囲

`ortools.sat.python.cp_model`をimportしてよいのは、原則として次に限定する。

```text
constraint/
service/timetable_solver_service.py
constraint/solver_context.py
```

`model`、`validator`、`adapter`、`composition`へOR-Tools型を漏らさない。

## 11. SolverContextの規約

`SolverContext`は、1回の探索処理に必要なOR-Tools固有状態を保持する。

保持してよいもの：

```text
CpModel
配置変数
日別授業有無変数
教師稼働変数
Candidate索引
ペナルティ項
変数名と業務キーの対応表
```

保持してはいけないもの：

```text
Excel Workbook
出力ファイルパス
Logger
Service
Adapter
入力検証結果
```

`SolverContext`はグローバル変数にせず、探索実行ごとに生成する。

## 12. Modelの設計規約

### 12.1 内部Modelは原則不変とする

内部Modelは、原則として`dataclass`の`frozen=True`および`slots=True`を使用する。

```python
@dataclass(frozen=True, slots=True)
class TeacherModel:
    teacher_id: str
    name: str
    subject_ids: tuple[str, ...]
    home_campus_id: str
```

例外：

- OR-Tools変数を保持する`SolverContext`
- 段階的に集計する必要がある内部Builder
- openpyxl等の外部ライブラリオブジェクト

### 12.2 Modelに業務処理を持たせすぎない

Modelに置いてよいメソッド：

- 値そのものの意味を返す軽量な判定
- 派生値を副作用なしで返す処理

```python
class ValidationReportModel:
    def has_errors(self) -> bool:
        return any(issue.is_error() for issue in self.issues)
```

Modelに置いてはいけない処理：

- Excel読込
- 制約構築
- 候補生成
- 日程最適化
- ログ出力
- ファイル保存
- 他Serviceの呼び出し

### 12.3 辞書の乱用禁止

業務データを`dict[str, Any]`でレイヤー間受け渡ししない。キーが固定されるデータはModelを定義する。

許容する辞書：

- IDからModelを引く索引
- OR-Tools変数の複合キー索引
- 外部ライブラリが要求する一時的な変換値

## 13. Adapterの設計規約

### 13.1 外部仕様をAdapterへ閉じ込める

次の処理はAdapterだけに置く。

```text
openpyxlによるWorkbook操作
シート名・列名・セル番地の解釈
Excel入力値の型変換
セル結合・書式・数式・印刷設定
ファイル入出力
テンプレートへの書き込み
```

### 13.2 Excel列名・シート名を散在させない

ワークシート名、ヘッダー名、固定セル番地はAdapter内の定数または専用Mapping Modelへ集約する。

悪い例：

```python
worksheet = workbook["04_クラス"]
class_id = row[0].value
exam_category = row[5].value
```

複数箇所で同じ文字列や列番号を使用してはならない。

推奨例：

```python
class ClassSheetMapping:
    sheet_name = "04_クラス"
    class_id_header = "class_id"
    exam_category_header = "exam_category"
```

### 13.3 Adapterで業務ルールを判断しない

Adapterは、外部値を内部Modelへ薄く変換する。

禁止例：

```python
if class_name == "梅光園3A":
    max_periods = 5
```

推奨：

```text
Excelで設定されたcampus_id、class属性、配置ルールを読み、
PlacementRuleModelへ変換するだけとする。
```

### 13.4 ReaderとWriterを分ける

1つのAdapterへ読込・出力・検証・テンプレート生成を詰め込まない。

```text
ExcelInputReaderAdapter
ExcelTimetableWriterAdapter
ExcelValidationReportWriterAdapter
ExcelTemplateWriterAdapter
```

## 14. Validatorの設計規約

### 14.1 Validationは境界で一度だけ行う

Validationは次の3段階に限定する。

| 段階 | 目的 | 配置 |
|---|---|---|
| 外部形式検証 | 必須シート、必須列、型、日付形式を確認 | AdapterまたはSchema Validator |
| 入力整合性検証 | ID参照、重複ID、固定授業の矛盾、明白な供給不足を確認 | `validator` |
| 結果検証 | 生成結果がHard Constraintを満たすことを独立確認 | `ValidateResultService`またはResult Validator |

Service間で受け渡す内部Modelは、入力検証済みとして扱う。

### 14.2 Validatorを細かく増やしすぎない

初期のValidatorは次の粒度を標準とする。

```text
WorkbookSchemaValidator
ReferenceIntegrityValidator
FixedLessonValidator
CapacityFeasibilityValidator
```

列ごと、項目ごと、単純な`if`ごとにValidatorクラスを作らない。

### 14.3 Validationと業務判断を分ける

```text
Validation:
  入力が読み取れ、参照が成立し、実行前提を満たすか

Constraint:
  時間割に許される配置を定義する

Diagnostic:
  解がない、または未配置が生じた理由を説明する
```

例：

```text
teacher_idが教師マスタに存在しない
  → Validation

同一教師を同じ時限へ2授業配置しない
  → Hard Constraint

教師休みを除いた候補枠が必要担当数より少ない
  → Capacity Feasibility ValidationまたはDiagnostic
```

### 14.4 無駄な防御的Validationを禁止する

次を禁止する。

- `None`を許容しない型に対する毎回の`None`チェック
- Model生成後の同一項目再検証
- Serviceごとの同じID存在確認
- Candidate生成時とConstraint適用時の同一条件再検証
- 「念のため」の空配列チェックを各所へ追加する
- 到達不能な状態にフォールバック値を返す

内部不変条件が破られた場合は、曖昧な継続より明示的な例外を優先する。

## 15. 関数・メソッドの切り出し規約

### 15.1 切り出してよい条件

次のいずれかを満たす場合のみ切り出す。

- 複数箇所から再利用される
- 独立した業務概念として名前を付けられる
- 単体テスト対象として分離する価値がある
- 公開メソッドの主要ステップを明確にする
- 外部ライブラリ依存を閉じ込める
- 1つのメソッド内で抽象度が大きく異なる処理を分離する

### 15.2 切り出してはいけない例

- 1回しか使わない2〜3行の代入
- 単純な`if`文のラップ
- 引数をそのまま別メソッドへ渡すだけ
- 名前を付けても業務上の意味が増えない
- テストのためだけにprivate methodを公開する
- 行数を減らすことだけを目的にする

### 15.3 モジュールレベル関数の制限

製造コードのモジュールレベル関数は、原則として次に限定する。

```text
main()
純粋かつ小規模な数式・キー生成処理
デコレータ
型ガード
```

業務処理、Excel処理、制約追加、検証処理はクラスのメソッドとして実装する。

### 15.4 private methodの命名

private methodは動詞から開始し、処理対象を含める。

推奨例：

```text
_load_input_data
_build_candidates
_create_solver_context
_collect_penalty_terms
_map_solver_result
```

禁止例：

```text
_process
_handle
_do_work
_check
_execute_internal
_helper
```

## 16. インターフェース方針

### 16.1 必要な側で定義する

Pythonでは`typing.Protocol`を使用し、差し替えが必要な依存を利用側の近くで定義する。

```python
class InputReader(Protocol):
    def read(self, path: Path) -> InputDataModel:
        ...
```

具体実装はAdapterに置く。

```python
class ExcelInputReaderAdapter:
    def read(self, path: Path) -> InputDataModel:
        ...
```

### 16.2 Protocolを作る基準

次のいずれかを満たす場合に限定する。

- Serviceが外部I/Oへ依存する
- 本番実装とテスト用Fakeを差し替える
- 複数の具体実装が実在する
- ライブラリ依存をServiceから排除する必要がある

初期段階でProtocolを作る価値が高いもの：

```text
InputReader
TimetableWriter
ValidationReportWriter
Clock（日時依存が発生した場合のみ）
```

原則としてProtocolを作らないもの：

```text
CandidateBuilder
Constraint
Validator
Mapper
Logger
IDGenerator
```

ConstraintとValidatorは具象クラスのシーケンスを注入すればよく、実装が1つしかない段階で抽象化しない。

### 16.3 `Interface`接尾辞禁止

```text
InputReaderInterface  ×
InputReader           ○
```

## 17. 依存方向の禁止事項

次の依存を禁止する。

```text
model → service
model → validator
model → constraint
model → adapter

service → openpyxl
service → Excelのシート名・列番号
service → composition

constraint → adapter
constraint → validator
constraint → openpyxl
constraint → 出力Modelの書式処理

adapter → constraint
adapter → serviceの具象実装

validator → adapterの具象実装

main.py → 個別Adapterの複雑な生成
```

依存関係の生成は`composition`へ閉じ込める。

## 18. データ駆動の必須原則

次の値をPythonコードへ直接埋め込まない。

```text

夏期・冬期等の季節名
日付
休館日
お盆期間
```

悪い例：

```python
if current_date.month >= 8 and class_model.grade == 3:
```

```python
matched_rules = rule_selector.select(
```

## 19. エラー処理規約

### 19.1 エラーを握りつぶさない

禁止例：

```python
try:
    ...
except Exception:
    return None
```

禁止例：

```python
try:
    ...
except Exception as exc:
    logger.warning("failed: %s", exc)
    return default_value
```

仕様にないフォールバックを追加してはならない。

### 19.2 捕捉する例外を限定する

外部ライブラリ例外はAdapterで捕捉し、文脈を付けたプロジェクト例外へ変換してよい。

```python
try:
    workbook = load_workbook(path)
except FileNotFoundError as exc:
    raise InputFileNotFoundError(path) from exc
except InvalidFileException as exc:
    raise InputWorkbookFormatError(path) from exc
```

`except Exception`は、CLI最上位でログを出して終了コードへ変換する場合を除き禁止する。

### 19.3 独自例外を増やしすぎない

初期は次のカテゴリで十分とする。

```text
ApplicationError
InputFileError
InputValidationError
SolverExecutionError
OutputFileError
```

セル、列、ルールごとに独自例外クラスを作らない。入力不備の詳細は`ValidationIssueModel`で表現する。

### 19.4 例外メッセージ

例外メッセージには、失敗した操作、対象、原因を含める。

```text
入力Excelの読込に失敗しました: path=..., sheet=04_クラス, cause=...
```

機密情報やWorkbook全体の内容をログへ出力しない。

## 30. 標準実装例

### 30.1 Hard Constraint

```python
from __future__ import annotations

from school_timetable_solver.constraint.solver_context import SolverContext


class TeacherOverlapConstraint:
    """H02: 同一教師の同一時限重複を禁止する。"""

    rule_id = "H02_TEACHER_OVERLAP"

    def apply(self, context: SolverContext) -> None:
        for variable_group in context.assignment_variables_by_teacher_slot.values():
            context.model.add(sum(variable_group) <= 1)
```

### 30.2 Validator

```python
from __future__ import annotations

from school_timetable_solver.model.input_models import InputDataModel
from school_timetable_solver.model.result_models import ValidationIssueModel


class ReferenceIntegrityValidator:
    def validate(
        self,
        input_data: InputDataModel,
    ) -> list[ValidationIssueModel]:
        teacher_ids = {teacher.teacher_id for teacher in input_data.teachers}
        issues: list[ValidationIssueModel] = []

        for requirement in input_data.lesson_requirements:
            if requirement.primary_teacher_id not in teacher_ids:
                issues.append(
                    ValidationIssueModel.error(
                        code="UNKNOWN_PRIMARY_TEACHER",
                        message=(
                            "必要授業が存在しない主担当教師を参照しています: "
                            f"requirement_id={requirement.requirement_id}, "
                            f"teacher_id={requirement.primary_teacher_id}"
                        ),
                    )
                )

        return issues
```

### 30.3 Service

```python
from __future__ import annotations

from school_timetable_solver.model.input_models import GenerationRequestModel
from school_timetable_solver.model.result_models import GenerationResultModel


class GenerateTimetableService:
    def __init__(
        self,
        input_reader: InputReader,
        validators: tuple[InputValidator, ...],
        candidate_builder: CandidateBuilderService,
        solver_service: TimetableSolverService,
        result_validator: ValidateResultService,
        timetable_writer: TimetableWriter,
    ) -> None:
        self._input_reader = input_reader
        self._validators = validators
        self._candidate_builder = candidate_builder
        self._solver_service = solver_service
        self._result_validator = result_validator
        self._timetable_writer = timetable_writer

    def execute(
        self,
        request: GenerationRequestModel,
    ) -> GenerationResultModel:
        input_data = self._input_reader.read(request.input_path)
        validation_issues = [
            issue
            for validator in self._validators
            for issue in validator.validate(input_data)
        ]
        if any(issue.is_error() for issue in validation_issues):
            return GenerationResultModel.input_error(validation_issues)

        candidates = self._candidate_builder.execute(input_data)
        solver_result = self._solver_service.execute(input_data, candidates)
        result_issues = self._result_validator.execute(input_data, solver_result)

        result = GenerationResultModel.from_solver_result(
            solver_result=solver_result,
            validation_issues=validation_issues + result_issues,
        )
        self._timetable_writer.write(result, request.output_path)
        return result
```

この例でも、Excel処理、Candidate生成、Constraint適用、結果検証、出力を別責務へ分離し、`GenerateTimetableService`は処理順序だけを管理する。

## 32. 最終原則

本プロジェクトでは、コード量の少なさではなく、変更理由と配置場所の明確さを優先する。

新しい仕様を追加する場合の標準手順は次のとおりである。

```text
1. 要件またはrule_idを確定する
2. Hard / Soft / Validation / I/O / Use Caseのいずれかへ分類する
3. 本規約の配置決定ルールでファイルとクラスを確定する
4. 規定された公開メソッドへ実装する
5. 最小の成立ケース・違反ケース・境界ケースをテストする
6. 既存ValidationやConstraintとの重複がないことを確認する
7. 静的解析・単体テスト・Integration Testを実行する
```

上記で配置先を説明できない処理は、実装すべき処理として十分に定義されていない。曖昧なまま既存ファイルへ関数を増設してはならない。
