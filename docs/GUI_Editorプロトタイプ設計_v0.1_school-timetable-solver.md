# GUI Editorプロトタイプ設計 v0.1

## 1. 目的

夏期・冬期講習の時間割作成で利用者が現在行っている作業順と、紙の管理表の認知モデルに近いEditor構成を先に実装し、Human-in-the-loopでUIを評価する。

本版は画面構造評価用であり、Editor入力の永続化は対象外とする。Home、Excel Import、保存済み案件、実行ダイアログは既存実装を継続利用する。

## 2. 情報の配置方針

### 2.1 毎季の主導線

左ナビの上段に、講習ごとに確認・更新する情報を作業順に配置する。

1. 日程
2. 授業回数
3. 担当教師
4. 教師の休み
5. 配置条件
6. 入力確認

日程を先に確定し、その日程を前提に授業数・担当・休み・例外条件を調整してから実行前確認を行う。

### 2.2 共通設定

毎季ほぼ変わらない情報は主導線から分離し、左ナビ下段の「共通設定 > マスタ管理」に置く。

- 校舎・教室
- 教師基本情報
- クラス基本情報
- 教科
- 時限

講習作成者が毎季これらを通過する必要はない。

## 3. 各画面

### 3.1 日程

- 講習期間
- 日付別の①〜⑥利用可否
- 休館日
- 学校行事・模試等の備考
- 日付追加、一括ON、休館日の一括設定を想定

### 3.2 授業回数

紙の「授業回数」表と同様、クラスを行、教科を列にした横持ち表を基本とする。

- 校舎フィルタ
- クラス別・教科別必要コマ数
- 行合計
- 必要コマ合計、校舎別合計、昨季差は自動集計予定

教科列は本実装では教科マスタから動的生成する。

### 3.3 担当教師

紙の「担当者」表と同様、クラスを行、担任・教科を列にした表を基本とする。

- 校舎フィルタ
- 前回担当の引継ぎ導線
- クラス別の担任・教科担当
- 教師別予定コマ数を同画面で自動集計予定

### 3.4 教師の休み

- 教師 x 開講日のマトリクス
- 範囲選択による一括入力を想定
- 期間内の必要・希望休日日数

日付列は日程画面の設定から動的生成する。

### 3.5 配置条件

通常利用者には内部rule_idや汎用条件式を直接見せない。

主要条件を業務用語で表示する。

- クラスの利用可能時限
- 1日の授業上限
- 連続登校
- 教師の勤務条件
- 今期だけの例外

配置数ルール、担任授業期間、クラス組重複禁止等は「高度なルール」へまとめる。

### 3.6 入力確認

- 各入力カテゴリの検証状態
- 必要コマ数等の自動集計
- Validation issue一覧
- 将来はissueから該当画面へ直接遷移

### 3.7 マスタ管理

タブで以下を管理する。

- 校舎・教室
- 教師
- クラス
- 教科
- 時限

## 4. プロトタイプ制約

- 入力コントロールはUI評価用であり、値は保存しない。
- Excel Import済み案件の既存実行機能は従来どおりImport元コピーを入力として使用する。
- 新規作成案件の実行は引き続き無効。
- subject列、日付列等は保存契約実装時にProjectDocument/マスタから動的生成する。
- Solver、Constraint、Excel入出力契約は変更しない。

## 5. 次の判断

実機で以下をHuman-in-the-loopで確認した後、保存契約と各画面の本実装へ進む。

- 左ナビの名称と順序
- 「授業回数」と「担当教師」を分ける判断
- 紙と同じ横持ち表が入力しやすいか
- マスタ管理を下段に退避する位置
- 日程・教師休みのマトリクス操作性
- 配置条件をどこまで通常画面に出すか
